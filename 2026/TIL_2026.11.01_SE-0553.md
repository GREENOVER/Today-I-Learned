## Summary of Changes

현재 실행 중인 `Task`에 대한 **저렴하고, 안정적이고, 프로세스 내에서 유일한** 식별자를 추가해요. `Task.currentID`와 `Task`, `UnsafeCurrentTask`의 인스턴스 접근자가 불투명한 `Task.ID`를 반환하는데, 비용이 thread-local 읽기와 비슷한 수준이라 트레이싱이나 구조화된 로깅 같은 상시 계측(instrumentation)을 hot path에서도 쓸 수 있게 해줘요. 이 식별자는 관찰 결과와 태스크별 상태를 태스크에 귀속시키기 위한 것이고, 제어 흐름을 조종하기 위한 게 아니에요.

## Motivation

Swift Concurrency는 현재 태스크를 들여다보는 `withUnsafeCurrentTask`, `Task.currentPriority`, `Task.name` 같은 API를 제공해요. 대부분의 앱 코드에는 충분하지만, 매 이벤트마다 실행되는 상시 계측 경로를 위해 설계된 API는 아니에요.

트레이싱이나 구조화된 로깅 라이브러리가 모든 이벤트에 "어느 태스크에서 발생했는지"를 붙이려면, 이 귀속 비용이 사실상 공짜, 즉 수 나노초 수준이어야 해요. 사용자의 hot path에서 이벤트마다 실행되기 때문이에요. 지금 가장 가까운 방법은 `withUnsafeCurrentTask`에 숫자 식별을 뽑는 `unsafeBitCast`나 해시 가능한 값을 얻는 `hashValue`를 조합하는 건데, 제안서가 Apple Silicon(M 시리즈)에서 표준 라이브러리 opt 빌드로 측정한 바로는 런타임 진입점은 몇 나노초지만 이 방식은 약 15배 더 들어요. 벤치마크 설정과 방식별 수치는 pitch 스레드에 있어요.

클로저 형태의 API가 비싼 이유는 런타임 호출이 느려서가 아니에요. 제네릭 `withUnsafeCurrentTask` 진입점에서 클로저의 existential boxing, 동적 스택 할당, witness table 간접 참조, 타입 메타데이터 조회가 쌓이기 때문이에요.

참고로 이 제네릭 클로저 경로를 우회하는 자체 span 라이브러리는 같은 하드웨어에서 span 시작/종료 한 쌍을 약 25ns에 끝낼 수 있어서, 프로덕션에서도 계측을 켜둘 만해요. 저렴한 태스크 식별은 이걸 가능하게 하는 구성 요소 중 하나예요. 런타임은 이미 필요한 식별자를 유지하고 있으니, 안정적인 API로 노출하면 계측 라이브러리가 내부 런타임 진입점에 기대지 않고도 이 성능에 도달할 수 있어요.

이런 요구는 트레이싱에만 국한되지 않아요.

- **실시간/지연에 민감한 시스템** — 트레이딩 인프라, 오디오 파이프라인, 게임 엔진처럼 프로덕션 계측이 기본으로 켜져 있어야 하고 프로파일에서 사실상 보이지 않아야 하는 곳
- **프로파일러와 개발자 도구** — 관찰 대상 프로그램에 측정 가능한 비용을 주지 않고 샘플이나 이벤트를 태스크에 귀속시키려는 경우
- **lock-free 자료구조** — 태스크별 상태를 키로 관리하는데, 런타임이 해제된 태스크의 힙 주소를 재사용할 수 있어서 포인터 동일성은 위험한 경우
- **커스텀 executor** — 태스크별 회계처럼 태스크 식별자로 인덱싱한 side table이 필요한 경우
- **구조화된 로깅** — 모든 로그 줄에 원본 태스크 식별자를 메타데이터로 실어서, 여러 태스크가 한 스레드를 공유해도 나중에 태스크별 흐름을 복원할 수 있게 하는 경우

이 모든 경우의 요구는 같아요. 현재 태스크에 대한 안정적이고, 비교 가능하고, 해시 가능한 식별자를 한 자릿수 나노초 범위에서 얻는 것이에요.

## Proposed Solution

Swift 런타임이 이미 유지하고 있는 프로세스 내 유일한 태스크 식별자를 `Task`의 공개 API로 노출해요.

```swift
// Constrained to Task<Never, Never> so callers can write `Task.currentID`
// without specifying generic arguments — matches the shape of Task.sleep.
extension Task where Success == Never, Failure == Never {
  /// The identifier of the currently executing task, or `nil` if no Swift
  /// `Task` is currently running on this thread.
  public static var currentID: Task.ID? { get }
}
```

결과 타입으로는 새 불투명 값 타입이 도입돼요. 최상위에 선언하고 `Task`의 typealias로 노출해서, `Task.ID`가 `Task`의 제네릭 인자에 따라 갈라지는 타입 가족이 아니라 하나의 표준 타입이 되게 했어요.

```swift
@frozen
public struct TaskID: Sendable, Hashable {
  public var rawValue: UInt64 { get }
}

extension Task {
  public typealias ID = TaskID
}
```

`rawValue`는 64비트 정수 표현이 필요한 곳, 즉 바이너리 와이어 포맷, 공유 메모리 영역, 비 Swift 소비자와의 브리지에서 직렬화를 위해 쓰는 문서화된 탈출구예요. 이 타입에는 의도적으로 공개 이니셜라이저가 없어요. 이유는 Alternatives Considered에서 다뤄요.

같은 식별자를 들고 있는 `Task` 참조나 `UnsafeCurrentTask`에서도 읽을 수 있어요.

```swift
extension Task {
  public var id: Task.ID { get }
}

extension UnsafeCurrentTask {
  public var id: Task.ID { get }
}
```

`Task.ID` / `task.id`라는 이름은 Swift의 `Identifiable` 프로토콜 관례와 일부러 맞춘 거예요. 표준 라이브러리에서 식별자를 가진 타입에 대해 사용자가 이미 기대하는 이름과 같아져요.

hot path 계측은 이런 모습이 돼요.

```swift
@inline(__always)
func emit(_ event: Event) {
  let id = Task.currentID  // a few nanoseconds, no allocations
  buffer.append(event, taskID: id)
}
```

## Detailed Design

### Intended use and pitfalls

위 사용 사례들은 같은 모양이에요. 일이 일어나는 곳에서 식별자를 기록하고, 나중에 로그, 트레이스, 프로파일러 샘플, side table에서 찾아본다는 거죠. `Task.ID`는 관찰 결과와 태스크별 상태를 태스크에 귀속시키는 키이지, 어느 태스크가 실행 중인지에 따라 제어 흐름을 바꾸는 방법이 아니에요. 태스크 식별자로 분기하는 코드는 스레드 식별자로 분기하는 코드와 같은 의심을 받아야 해요. 특히 다음을 주의해야 해요.

- **태스크 구조는 계약이 아니에요.** 어떤 API가 호출자가 준 클로저를 호출 태스크에서 돌리는지 자식 태스크에서 돌리는지는, 그 API가 문서화하지 않았다면 구현 세부사항이에요. 문서화 없이 `Task.currentID`를 알려진 `task.id`와 비교하면, 릴리스 사이에 바뀔 수 있는 구현의 우연을 관찰하는 셈이에요.
- **취소는 컨텍스트 안에서 관찰되지만, 식별자는 그렇지 않아요.** 태스크 취소 방패([SE-0504](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0504-task-cancellation-shields.md)) 안에서는, 바깥 스코프에서 취소된 태스크의 `Task.isCancelled`는 `false`를 보고하지만 그 태스크의 핸들에 대한 `task.isCancelled`는 `true`를 보고해요. `Task.ID`는 두 관찰이 같은 태스크에 대한 것임을 확인해줄 수 있어요. 그건 식별자가 제 역할을 하는 것이지, 의지하거나 우회해야 할 모순이 아니에요.
- **식별자는 핸들이 아니에요.** `Task.ID`로는 태스크를 취소하거나 await하거나 접근할 수 없고, 부모/자식, 그룹, executor 관계도 담고 있지 않아요. 자식 태스크로 일을 따라가야 하는 값은 식별자 키 side table이 아니라 태스크 로컬([SE-0311](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0311-task-locals.md))을 통해 자동으로 상속돼요.
- **side table은 소유자가 정리해야 해요.** 식별자는 재사용되지 않으므로 오래된 항목이 이후 태스크에 의해 회수되지 않아요. `Task.ID`를 키로 쓰는 테이블(예: 커스텀 executor의 태스크별 회계)은 소유자가 항목을 비우지 않으면 끝없이 커져요.

태스크 식별은 이미 디버거, Instruments, `swift-inspect`, 또는 `UnsafeCurrentTask`의 포인터 동일성으로도 관찰할 수 있어요. 이 제안은 그걸 필요한 계측에 맞게 저렴하고 안정적으로 만들 뿐이고, 런타임 동작으로 가는 우회 채널로 쓰는 건 권장하지 않아요.

### Task.ID

`Task.ID`는 런타임이 만든 64비트 부호 없는 정수를 감싼 불투명 값 타입이에요. 기반 정수는 직렬화를 위해 `rawValue`로 꺼낼 수 있고, 공개 이니셜라이저는 없어요.

```swift
@frozen
public struct TaskID: Sendable, Hashable {
  public var rawValue: UInt64 { get }
}

extension Task {
  public typealias ID = TaskID
}
```

이 구조체를 `Task` 안에 중첩하지 않고 최상위에 선언한 이유가 있어요. `Task`는 `Success`, `Failure`에 대해 제네릭이라, 직접 중첩한 `Task.ID`는 `Task<Success, Failure>.ID`, 즉 인스턴스화마다 별개의 타입이 되어버려요. 단일 표준 식별자 타입에는 맞지 않는 모델이죠. typealias는 사용자에게는 `Task.ID` 표기를 주면서 기반 타입은 하나로 유지해줘요.

이 구조의 결과로 `Task.ID`와 기반 `TaskID`는 같은 타입으로 해석되고 호출 지점에서 둘 다 쓸 수 있어요. `Task.ID`가 표준이고 문서화된 표기라서 이쪽을 선호해야 하고, `TaskID`는 Swift의 이름 해석이 제네릭 enclosing 타입 안에 비제네릭 타입을 공개적으로 중첩하는 걸 지원하지 않기 때문에 존재하는 비매개변수 기반 타입이에요.

이 타입은 두 가지 사용 형태를 위한 거예요. **프로세스 내 소비자**는 태스크 식별자로 키를 잡은 딕셔너리, 살아 있는 태스크의 집합, 모듈 경계를 넘어 식별자를 나르는 타입 있는 API 파라미터처럼 `Task.ID`를 직접 다루고 기반 정수를 건드릴 일이 없어요. **와이어 포맷과 다른 언어 소비자**는 `rawValue`를 꺼내 안정적인 64비트 정수를 전송해요. API는 두 경우 모두 편하도록 만들어졌어요.

`rawValue`는 래퍼에서 나오는 유일하게 지원되는 탈출구예요. 와이어 포맷 작성자는 생산자 쪽에서 `rawValue`를 내보내고, 소비자 쪽에서는 그 값을 불투명한 정수로 취급해요. 소비자는 보통 로그를 남기거나, 키로 쓰거나, 다른 데이터와 조인하기 위해 `Task.ID` 인스턴스를 복원할 필요가 없어요. 직렬화된 값은 관찰 결과(로그, 트레이스, 다른 데이터와의 조인)를 내보내기 위한 것이지, 다른 프로세스에서 태스크 동일성을 단언하기 위한 게 아니에요. 다른 프로세스에서 그 값은 64비트 정수라는 것 외에는 의미 보장이 없어요. `MemoryLayout<Task.ID>.size`는 `@frozen`으로 고정된 컴파일 타임 상수 `8`이에요.

`Codable`, `Encodable`, `Decodable` 채택은 제안하지 않아요. 문서화된 직렬화 경로는 호출자가 쓰는 스키마에 `rawValue`를 직접 인코딩하는 거예요. 채택을 넣으면 스키마 설계가 정해야 할 인코딩 표현을 표준 라이브러리가 대신 고르게 되거나, `rawValue`가 이미 제공하는 걸 중복하게 돼요. 사용 사례가 생기면 별도 제안에서 고려할 수 있어요.

식별자는 다음 의미를 보장해요.

- **프로세스 내 유일:** 같은 프로세스에서 살아 있는 두 태스크는 항상 서로 다른 식별자를 가져요.
- **재사용되지 않음:** 한 번 부여된 식별자는 원래 태스크가 소멸된 뒤에도 다른 태스크에 다시 부여되지 않아요. 오래 사는 side table의 키로 안전하게 만드는 속성이고, 포인터 동일성이 주는 것보다 강한 보장이에요.
- **태스크 수명 동안 안정:** 태스크 생성 시점에 정해지고 바뀌지 않아요.
- **프로세스 간에는 안정적이지 않음:** 식별자는 프로세스 로컬이라, 프로세스 간에 의미가 있을 거라 기대하며 저장하거나 전송하면 안 돼요.

런타임은 현재 식별자를 단조 증가로 할당하지만, 이건 구현 속성이지 계약의 일부가 아니에요. `Task.ID`는 `Comparable`을 채택하지 않아요. `rawValue`는 직렬화를 위해 노출된 것이지 순서 추론을 위한 게 아니에요. 위 보장이 유지되는 한, 미래 런타임은 카운터를 샤딩하거나, 시작 시점 nonce를 섞거나, 할당 방식을 바꿔도 소스를 깨지 않아요.

카운터 공간 고갈(한 프로세스에서 2⁶⁴번의 식별자 할당)은 명세된 동작이 아니에요. 64비트 공간은 현실적인 프로세스 수명 안에서 도달할 수 없을 만큼 커서(초당 10억 번 태스크를 할당해도 한 바퀴 도는 데 약 584년), 제안은 특정 결과를 강제하지 않아요.

### Task.currentID

```swift
extension Task where Success == Never, Failure == Never {
  public static var currentID: Task.ID? { get }
}
```

이 제약은 오늘날 `Task.sleep` 같은 static 멤버가 선언되는 방식을 따라요. static 접근자는 `Success`, `Failure`에 의존하지 않으므로, 표준 `Task<Never, Never>` 네임스페이스에 묶으면 호출자가 제네릭 인자를 지정하지 않고도 `Task.currentID`라고 쓸 수 있어요.

이 스레드에서 현재 실행 중인 태스크의 식별자를 반환하고, 현재 실행 중인 Swift `Task`가 없으면 `nil`을 반환해요(예: 동시성 런타임 밖에서 시작한 동기 컨텍스트에서 호출한 경우). 이 접근자가 성능이 가장 중요한 진입점이에요. 설계 목표는 thread-local 읽기에 견줄 만한 한 자릿수 나노초이고, 할당은 없어요.

### Instance accessors

```swift
extension Task {
  public var id: Task.ID { get }
}

extension UnsafeCurrentTask {
  public var id: Task.ID { get }
}
```

`Task.id`는 태스크가 끝난 뒤에도 항상 안전하게 호출할 수 있어요. 식별자는 태스크 생성 시점에 고정되어 이후 바뀌지 않으므로 동기화가 필요 없어요.

`UnsafeCurrentTask.id`는 `UnsafeCurrentTask`의 다른 모든 프로퍼티와 같은 안전 계약을 가져요. unsafe 태스크 참조는 태스크를 살려두지 않으므로, 해제된 태스크에서 읽는 건 정의되지 않은 동작이에요. 다만 반환값이 trivial 값 타입이라, `withUnsafeCurrentTask` 클로저 안에서 식별자를 읽어두면 클로저가 끝난 뒤에도 그 값을 계속 쓸 수 있어요.

### Performance contract

런타임은 이미 모든 태스크에 대해 64비트 식별자를 유지하고 있어서, 구현은 그 필드를 호출자가 믿을 수 있는 비용으로 안정적인 API를 통해 노출하는 문제예요. 이 제안이 구현에 요구하는 계약은 이래요.

- `Task.currentID`의 평상시 비용은 최신 Apple Silicon에서 한 자릿수 나노초이고, 다른 최신 64비트 하드웨어에서도 비슷해야 해요. thread-local 읽기보다 비싸면 안 돼요.
- 할당이 없고, 일반 경로에서 동적 디스패치도 없으며, 기반 런타임 읽기가 이미 요구하는 것 이상의 동기화도 없어요.
- `Task`와 `UnsafeCurrentTask`의 인스턴스 접근자도 같은 비용 특성을 제공해요.
- `Task.ID`의 합성된 `Equatable`, `Hashable` 연산은 구체 타입 호출 지점에서 `UInt64` 대응 연산과 같은 명령어 시퀀스로 컴파일돼요.

구체적인 인라이닝 전략, ABI 심볼 모양, back-deployment 하한은 구현 리뷰에서 다룰 문제예요.

`Task.ID`는 레이아웃을 고정하기 위해 `@frozen`이에요. 이건 인라이닝 힌트가 아니라 API 계약의 일부예요. `rawValue` 접근자와 `MemoryLayout<Task.ID>.size == 8` 보장이 둘 다 여기에 의존해요. 64비트 폭도 `rawValue`를 통해 계약의 일부예요. 다만 그 비트의 내부 *해석*(예: `(generation, slot)` 쌍으로 나누거나 프로세스 시작 nonce를 섞는 것)은, 프로세스 내 유일하고 재사용되지 않는다는 의미 보장이 유지되는 한 구현이 자유롭게 정할 수 있어요.

### Interaction with task names

`Task.name`([SE-0469](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0469-task-names.md))은 태스크 생성 시점에 부여하는 사람이 읽는 레이블이에요. 이 제안의 식별자는 그와 상호 보완적이에요. 작고, 저렴하고, 항상 존재하고, 프로세스 내에서 유일하죠. 계측 시스템은 식별자를 조인 키(로그, 테이블, side 자료구조)로 쓰고, 사람이 보도록 렌더링할 때만 이름을 만들어 쓰기를 기대해요. OS 스레드가 숫자 `tid`와 선택적인 pthread 이름을 둘 다 갖는 것과 같아요.

## Source / ABI Compatibility, Adoption

**Source:** 순수하게 추가만 하는 변경이라 기존 코드는 변경 없이 컴파일돼요.

**ABI:** 공개 API 수준에서 순수하게 추가만 하고, 기존 타입이나 진입점은 수정하지 않아요. 새 `Task.ID` 타입은 `UInt64` 페이로드 하나를 가진 `@frozen`이라, 레이아웃은 API가 출시되는 날부터 ABI의 일부예요. 구현이 새 ABI 심볼을 도입하는지, 기존 런타임 진입점만으로 만드는지는 구현 리뷰의 문제예요.

**Adoption:** 배포 하한은 Performance contract에서 논의한 구현 선택에 달려 있어요. 그 외에는 순수하게 추가만 하는 기능이라, 소스 코드에서 자유롭게 채택하거나 빼도 채택하는 라이브러리의 클라이언트에는 소스/ABI 호환성 영향이 없어요.

## Future Directions

### Comparable 채택

`Task.ID` 항목에서 말했듯이 순서는 API 계약의 일부가 아니라서 `Comparable`을 채택하지 않아요. 사용 사례가 생기면 별도 제안에서 고려할 수 있어요.

### 프로세스 간 상관관계

프로세스나 호스트 경계를 넘는 분산 트레이싱에는 이 제안의 식별자로는 의도적으로 충분하지 않아요. 프로세스 로컬이기 때문이에요. 프로세스 간 상관관계는 자체적으로 전역 유일 식별자를 만드는 `swift-distributed-tracing` 같은 라이브러리의 영역으로 남아요.

## Alternatives Considered

### 포인터 동일성을 대신 노출하기

가장 직접적인 대안은 원시 태스크 포인터를 (`UnsafeRawPointer`나 불투명 타입으로 감싸서) 노출하는 거예요. 오늘날 대부분의 호출자가 `unsafeBitCast`로 손을 뻗는 방식이에요. 이건 한 가지 주된 이유로 거부했어요. 런타임은 소멸된 태스크의 힙 주소를 자유롭게 재활용할 수 있어요. 그래서 포인터 동일성을 키로 쓴 오래 사는 side table은, 우연히 같은 주소를 쓰게 된 서로 다른 두 태스크를 조용히 혼동할 위험이 있어요. 태스크별 메타데이터(이름, span 컨텍스트 등)를 캐시하는 계측 시스템이라면, 사후에 진단하기가 사실상 불가능한 잘못된 귀속으로 이어져요. 재사용되지 않는 프로세스 내 유일 식별자는 이 버그 계열 전체를 없애줘요.

### withUnsafeCurrentTask를 대신 저렴하게 만들기

원칙적으로 제네릭 클로저 경로를 특수화하거나, `@inlinable` shim을 추가하거나, 비제네릭 오버로드를 도입해서 `withUnsafeCurrentTask`의 비용을 줄일 수 있어요. 검토했지만, 최선의 경우에도 `UnsafeCurrentTask?` 값을 만들고 넘기는 비용은 남고, 실제로 대부분의 호출자는 작은 식별자만 원해요. 직접 접근자가 더 단순하고 더 빠르고, `withUnsafeCurrentTask`를 이런 방향으로 개선하는 걸 막지도 않아요.

### UInt64를 직접 반환하기

접근자가 그냥 `UInt64?`를 반환해서 래퍼 타입을 피할 수도 있었지만 기각했어요. 맨 `UInt64?`는 호출 지점에서 의도를 문서화하지 못해요. 스레드 ID, 파일 디스크립터, 시퀀스 번호, 바이트 오프셋 등에도 같은 모양이 쓰여서, 함수 시그니처의 `taskID: UInt64?`는 그것들과 다르게 읽히지 않아요. Swift는 강타입 언어이고, 표준 라이브러리는 기반 표현이 프리미티브일 때도 식별자와 수량에 일관되게 별개의 명목 타입을 써요. `ObjectIdentifier`, `Duration`, `Unicode.Scalar`가 모두 이 패턴을 따라요. `Task.ID`도 같은 부류예요. 타입 혼동의 구멍을 타입 시스템 수준에서 막고, 부수 효과로 `id + 1` 같은 무의미한 연산을 컴파일러가 막아줘요.

래퍼의 런타임 비용은 0이에요. 사소한 `UInt64` 페이로드 하나를 가진 `@frozen`은 맨 `UInt64`와 같은 머신 코드로 내려가고 같은 레지스터로 전달돼요. 구체 타입 호출 지점에서는 합성된 `Equatable`/`Hashable` 연산도 `UInt64` 대응 연산과 같은 명령어 시퀀스로 컴파일돼요.

### RawRepresentable 채택이나 공개 이니셜라이저 제공

이 타입은 `rawValue`를 노출하지만 `UInt64`로 식별자를 만드는 방법은 없어요. 관련된 두 가능성을 검토했어요.

**RawRepresentable 채택.** 정수를 감싼 타입 래퍼에 자연스러워 보이는 모양이고, `RawValue: Codable`이면 `Codable` 합성도 공짜로 얻을 수 있었어요. 하지만 이 프로토콜은 실패 가능한 `init?(rawValue:)`를 요구해요. 일부 raw 값만 유효한 enum 같은 타입을 위해 만들어진 거죠. `Task.ID`에서는 모든 `UInt64`가 구조적으로 유효한 식별자예요. 런타임이 사후에 어떤 정수를 발급했는지 알 수 없고, 와이어에서 받은 raw 바이트를 검증할 수 있는 수신자도 없어요. 채택하면 어떤 입력에도 `nil`을 반환하지 않는 이니셜라이저를 내놓고, 모든 호출자가 `.none`일 수 없는 `Optional`을 풀게 만들어요. 잘못된 기본값이에요.

**프로토콜 채택 없이 실패하지 않는 `init(_ rawValue: UInt64)` 제공** (`os.OSSignpostID`의 선례를 따라). 여기에 대한 반대는 편의가 아니라 의미 문제예요. `Task.ID` 값은 *런타임이 발급*해요. 임의의 정수로 하나를 합성하면 이 프로세스의 어떤 태스크에도 대응하지 않는 값이 만들어져요. 소비자 쪽 와이어 포맷 코드 대부분은 사실 `Task.ID`를 복원할 필요가 없어요. 정수를 로그로 남기거나, 딕셔너리 키로 쓰거나, 다른 데이터와 조인하는데, 모두 맨 `UInt64`로 가능해요. 래퍼는 런타임이 타입 있는 값을 건네주고 타입 시스템이 관련 없는 정수와의 혼동을 막아주는 *생산자* 쪽에서 가장 가치 있어요.

선택한 모양, 즉 단방향 추출용 `rawValue`, 공개 이니셜라이저 없음, `RawRepresentable` 채택 없음은 이 비대칭을 반영해요. 제안은 의도적으로 지원되는 복원 API를 제공하지 않고, unsafe 도구는 의미 계약 밖에 남겨둬요.

### 예약된 sentinel을 쓴 non-optional Task.ID 반환하기

`Task.currentID`는 `Task.ID?`를 반환하도록 명세돼 있고, `nil`은 이 스레드에서 Swift `Task`가 실행 중이 아님을 뜻해요. `UInt64`에는 여유 비트가 없어서, 현대 64비트 Swift ABI에서 `Optional<Task.ID>`는 16바이트이고 레지스터 두 개로 반환돼요. 무조건적인 `Task.ID`는 8바이트에 레지스터 하나예요. hot path에서는 작지만 실제로 있는 차이예요.

대안은 `Task.ID` 안의 값 하나(런타임이 오늘날 절대 할당하지 않는 0이 가장 자연스러워요)를 "현재 태스크 없음"으로 예약하고 non-optional `Task.ID`를 반환하는 거예요. 이러면 정적 타입 시스템 안전성을 약간 포기하는 대신(호출자가 `Optional`을 풀지 않고 `id != .none`을 확인해야 해요), 눈에 띄게 저렴한 반환 규약과, 부재 케이스를 신경 쓰지 않고 받은 값을 그냥 저장하는 흔한 경우의 약간 더 단순한 호출 지점을 얻어요.

제안에서는 `Task.ID?`를 선택했어요. "없을 수 있음"에 대한 관용적인 Swift 모양이고, 부재 케이스가 아주 드물지는 않기 때문이에요(동시성 런타임 밖에서 부르는 동기 호출자). sentinel 형태는 `currentID`에 영향 없이 별도 이름의 non-optional 접근자로 나중에 추가할 수 있어요. 이건 래퍼 타입이 가능하게 해주는 여지 중 하나이고, 맨 `UInt64?`로는 불가능했을 거예요.

### 사용자 코드에서 식별자 합성하기

라이브러리가 태스크 로컬을 붙이거나, `withUnsafeCurrentTask` 기반 side table을 유지하는 식으로 자체 식별자를 할당할 수 있어요. 이런 방식은 모두 위에서 설명한 포인터 재사용 문제를 그대로 물려받거나, 매 emit마다 `withUnsafeCurrentTask` 오버헤드를 내거나, 둘 다예요. 런타임은 이미 우리가 원하는 식별자를 유지하고 있어서, 빠진 건 그걸 저렴하게 읽는 방법뿐이에요.

### UnsafeCurrentTask에만 API 두기

식별자를 `UnsafeCurrentTask`에만 노출하고 호출자가 `withUnsafeCurrentTask`를 거치게 하는 안도 검토했어요. 기존 API 모양은 유지되지만, 이 제안의 핵심인 성능 이점이 통째로 사라져요.

## Acknowledgments

태스크 포인터 대신 런타임에 이미 있는 단조 증가 `task_id`를 노출하자고 제안해서, 이 제안의 방향을 바꾼 **Franz Busch**에게 감사드려요. 기반 런타임 필드를 ABI 안정적으로 만들 수 있음을 확인해준 **John McCall**, "재사용되지 않음" 보장의 근거가 된 포인터 재사용 위험을 짚어준 **tera**에게도 감사드려요. [pitch 스레드](https://forums.swift.org/t/pitch-cheap-task-identity-for-high-performance-instrumentation/86666)의 다른 참여자들께도 감사드려요.

## Conclusion

그동안 태스크를 식별하려면 `withUnsafeCurrentTask`를 거쳐야 해서 상시 계측에는 비용이 너무 컸고, 포인터를 키로 쓰면 주소 재사용 때문에 위험했어요. `Task.currentID`는 런타임이 이미 갖고 있는 "재사용되지 않는 64비트 식별자"를 thread-local 읽기 수준의 비용으로 꺼내 쓰게 해주는 작은 API예요. 다만 식별자는 제어 흐름용이 아니라 관찰과 귀속을 위한 키라는 점을 제안서가 분명히 강조하고 있는 것도 인상적이었습니다 🙌
