## Intro

- **Proposal**: SE-0557
- **Author**: Jeremy Schonfeld
- **Review Manager**: Joe Groff
- **Status**: Accepted
- **Implementation**: swiftlang/swift#93187

## Summary of Changes

`RawSpan`의 바이트를 `Hasher`의 상태에 섞어 넣는 새 프리미티브 API를 `Hasher`에 추가해요. 한 줄로 요약하면, `UnsafeRawBufferPointer`를 받던 기존 프리미티브의 **안전한 버전**이 생긴다는 제안이에요.

## 배경: Hasher의 두 가지 입력 경로

제안을 이해하려면 `Hasher`에 데이터를 넣는 방법부터 짚어두는 게 좋아요. 제안서는 현재 `Hasher`가 상태에 데이터를 섞는 주된 API를 두 가지로 정리해요.

| 구분           | 입력                     | 동작                              |
| -------------- | ------------------------ | --------------------------------- |
| 제네릭 API     | 임의의 `Hashable` 값     | 그 값의 `hash(into:)` 구현에 위임 |
| 프리미티브 API | `UnsafeRawBufferPointer` | 버퍼의 내용을 직접 섞어 넣음      |

첫 번째는 타입이 `Hashable`을 채택해서 `hash(into:)`를 제공하는 일반적인 경로예요. 두 번째는 이미 메모리에 있는 바이트 덩어리를 그대로 해시에 반영하고 싶을 때 쓰는 낮은 수준의 경로고요.

## Motivation

문제는 두 번째 경로가 `UnsafeRawBufferPointer`를 요구한다는 점이에요. Swift에는 이제 `UnsafeRawBufferPointer`의 안전한 대안인 `RawSpan` 타입이 있어요. 그런데 `Hasher`의 프리미티브 API를 쓰려면 여전히 unsafe API에 기대야 하죠.

제안서의 입장은 명확해요. 개발자는 **unsafe API에 의존하지 않고도** `Hasher`의 프리미티브 API를 쓸 수 있어야 한다는 거예요.

## Proposed Solution

`RawSpan`을 인자로 받는 새 프리미티브 API를 `Hasher`에 추가해요. 제안서가 보여주는 사용 예시는 이렇게 돼요.

```swift
var values: InlineArray<_, UInt8> = /* ... */

var hasher = Hasher()
hasher.combine(bytes: values.span.bytes)
```

`InlineArray`에서 `span`을 얻고, 그 `bytes`(`RawSpan`)를 바로 `combine(bytes:)`에 넘기는 모양이에요. 포인터를 꺼내거나 `withUnsafe...` 클로저를 거칠 필요가 없어요.

### 기존 방식과 비교해보기

> 아래 비교 코드는 제안서의 예시가 아니라, 이해를 돕기 위해 제가 구성한 설명용 예시예요. 기존 프리미티브가 `UnsafeRawBufferPointer`를 받는다는 제안서의 설명에 맞춰 작성했어요.

```swift
let bytes: [UInt8] = [1, 2, 3, 4]

// 기존: UnsafeRawBufferPointer를 얻는 unsafe API를 거쳐야 함
var oldHasher = Hasher()
bytes.withUnsafeBytes { buffer in
    oldHasher.combine(bytes: buffer)
}

// 제안 후: RawSpan을 바로 넘김 (unsafe API 불필요)
var newHasher = Hasher()
newHasher.combine(bytes: bytes.span.bytes)
```

## Detailed Design

제안되는 API는 하나뿐이에요.

```swift
extension Hasher {
    @export(implementation)
    public mutating func combine(bytes: RawSpan)
}
```

기존 `combine(bytes: UnsafeRawBufferPointer)`와 인자 레이블(`bytes:`)이 같고 타입만 달라서, 기존 프리미티브의 자연스러운 짝이 돼요. 시그니처에 붙은 `@export(implementation)`는 구현 쪽 어트리뷰트로, 제안서도 별도 설명 없이 시그니처에만 표기하고 있어요.

### Source Compatibility

소스 호환성에는 영향이 없을 것으로 봐요. 새 API는 기존 API를 오버로드하지만, `UnsafeRawBufferPointer`와 `RawSpan`은 서로 모호하지 않아요. 호출 지점에서 어느 쪽을 넘기는지에 따라 오버로드가 명확히 갈립니다. 또 클라이언트가 직접 제공한 같은 API 구현이 있다면, 표준 라이브러리가 제공하는 버전보다 우선해서(shadow) 동작해요.

### ABI Compatibility

ABI 호환성에는 영향이 없어요.

### Implications on Adoption

이 API는 소스 코드에서 자유롭게 채택하거나 빼도 돼요. 다만 `RawSpan` 타입 자체를 쓸 수 있을 만큼 최신인 배포 타깃이 전제예요.

## Future Directions

### RawSpan의 Hashable 채택

앞으로 `RawSpan` 자체를 `Hashable`로 만드는 것도 고려해볼 수 있어요. 조사해볼 가치가 있지만, 이 제안은 오직 기존 `Hasher` 프리미티브를 더 새로운 표준 라이브러리 타입과 동등한 수준으로 맞추는 데에만 집중해요.

만약 `RawSpan`이 `Hashable`을 채택하게 되면, 기존 제네릭 API인 `combine<H: Hashable>(_:)`에도 `RawSpan`을 넘길 수 있게 돼요. 그렇다고 이 제안의 API가 필요 없어지는 건 아니에요. `RawSpan`이 제네릭 `combine`의 유효한 인자가 되더라도, unsafe API를 쓰지 않고 바이트를 해시하는 프리미티브 API는 여전히 제공할 가치가 있기 때문이에요.

## Conclusion

작지만 방향이 분명한 제안이에요. `RawSpan`이 `UnsafeRawBufferPointer`의 안전한 대안으로 자리 잡아가는 만큼, 표준 라이브러리의 기존 프리미티브들도 그 타입을 받도록 정리해주는 작업이라고 볼 수 있어요. `Hasher.combine(bytes:)`에 `RawSpan` 오버로드가 생기면서, 바이트를 해시에 섞는 코드에서도 unsafe 없이 `Span` 계열 API와 자연스럽게 이어 쓸 수 있게 됩니다 🙌
